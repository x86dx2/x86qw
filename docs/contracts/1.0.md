# Public contracts of the 1.0 line (history)

> A record of the Python 1.0 line. The 2.x CLI keeps the JSON envelope
> (`schema_version` 1) and the exit codes 0, 1, 2 and 130 described here; the
> rest, such as installer bundles, `current` and the 0.7.x versions, describes
> that line. The current state is in [PROJECT-STATUS.md](../PROJECT-STATUS.md).

This document defines the contracts that must stay stable before a `1.0.0`
version. The current public version (`0.7.13`) stays immutable; these
contracts enter validation first and do not change the `current` catalog on
their own. The public `0.7.13` catalog is still a legacy document with
`format: 1`, now authenticated by the standard TUF chain; emitting
`catalog_version` and `min_cli_version` belongs to the regeneration and
signing of a later 1.0 catalog.

## Versioning

- component and candidate versions follow SemVer, including `-alpha`, `-beta`
  and `-rc`; numeric components have no leading zeros and build metadata does
  not change precedence;
- the installer's public bundle stays, in this contract, a stable `x.y.z`
  version: the historical validators and the `0.7.x` bootstraps do not accept
  prereleases. A future `alpha`, `beta` or `rc` publication needs an explicit
  change to the bundle contract, to the four synchronized bootstraps and to
  the ordering of `latest`; the 1.0 gate does not accept it implicitly;
- each catalog, state and receipt declares its own schema version;
- documents with an explicit schema also declare `min_cli_version`; a
  `max_cli_version` is only valid together with the minimum, and both are
  checked before any mutation;
- historical documents that only carry `format` stay readable in the legacy
  compatibility mode;
- old clients use immutable snapshots and do not depend on a moving `main`.

The current document versions are `catalog_version: 1`, `state_version: 2`
and `receipt_version: 1`. A document that explicitly picks one of those
versions declares `min_cli_version`; `max_cli_version` is optional, but cannot
appear alone. Legacy documents that only carry `format` stay with the
compatibility reader and are not rewritten automatically.

### Channels and deprecation

`alpha`, `beta`, `rc` and `stable` are SemVer channels; each published version
points to an immutable coordinate (`refs/tags/...`, `commit/<sha>` or
`snapshot/<sha256>`). `nightly` keeps the historical identifier
`YYYYMMDD-HHMMSS_<sha7>` and also points to immutable snapshots; a moving
nightly pointer can only be resolved when explicitly enabled and is never
persisted as the identity the client consumed. SemVer precedence is the
official one: alpha < beta < rc < stable, and build metadata does not change
the ordering.

Deprecations are monotonic: `active` → `deprecated` → `removed`. A field
cannot be removed without first being marked deprecated; any document that
declares `removed_in` must also declare `deprecated_in`, and the removal
version cannot precede it. Clients must respect the declared compatibility
window before accepting a mutation.

## State and output

`version`, `status`, `hub`, `verify`, `doctor`, `repair --dry-run`,
`update --dry-run` and `upgrade --dry-run` can produce canonical JSON without
ANSI, prompts or secrets. The stable codes are `0` (success), `1` (operational
failure), `2` (invalid usage or contract) and `130` (interruption); no other
code may appear in the public JSON envelope.

Migrations only remove or replace a file when the receipt, the inventory and
the file's identity prove ownership. Personal settings, demos, logs, PAKs and
files without proven ownership are kept.

### JSON envelope and per-command data

The JSON envelope has exactly these fields: `schema_version` (the integer
`1`), `command`, `ok`, `exit_code`, `dry_run`, `data` and `errors`. The output
is UTF-8, canonical, sorted by key and ends with a single line break; unknown,
missing or duplicate fields are rejected. `ok: true` uses `exit_code: 0` and
`errors: []`. `ok: false` uses a stable non-zero code, keeps `data: {}` and
brings at least one error with exactly `code` and `message`. The `dry_run`
field is always `false` for `version`, `status`, `hub`, `verify` and `doctor`,
and always `true` for the three maintenance commands exposed in JSON.

For a successful response, `data` is closed per command:

| command | exact shape of `data` |
| --- | --- |
| `version` | `{project: "x86qw", version: <SemVer>}` |
| `status` | `{project: "x86qw", target: string, installation: "present"\|"missing", state: "present"\|"missing", sessions: [{session_id: string, status: string, command: string}]}` |
| `hub` | `{target: string, servers: [{address: host:port, title: string, mode: string, map: string, players: {humans: integer, bots: integer}, qtv_stream: string\|null}]}` |
| `verify` | `{target: string, verified: true}` |
| `doctor` | `{target: string, audience: "owner-only", healthy: boolean, checks: [{id: string, status: "ok"\|"warn"\|"fail"\|"skip", summary: string}]}` |
| `repair`, `update`, `upgrade` with `--dry-run` | `{target: string, status: "noop"\|"planned"\|"blocked", operations: [{kind: string, item: string, installed: string, available: string, action: string, size: integer\|null}]}` |

`doctor.checks` holds exactly these ids, in this order: `installation`,
`catalog`, `trust`, `runtime`, `network`, `disk` and `permissions`. `healthy`
is `true` only when no check has the `fail` status. The network is not
queried by default (`skip`); that keeps the command deterministic and
offline. `doctor --bundle` writes a reviewable zip with `NOTICE.txt` and the
same sanitized envelope; the stdout JSON schema gains no fields. With
`--json --bundle`, the zip's path goes to stderr.

The `status.sessions` and `hub.servers` lists are sorted deterministically
(by `session_id` and `address`, respectively), and accept neither duplicates
nor upstream fields. The Hub only exposes that minimal projection: tokens,
credentials, URLs with credentials and the raw object the service returns are
not part of the contract. `noop` holds no operations; `planned` holds at least
one; `blocked` may be empty. The shape of `data` is part of the API: any
change of fields, types, enumerations or ordering needs a new
`schema_version`; clients must reject versions they do not know.

To keep the output predictable, text in `data` has at most 4096 characters;
`sessions` accepts up to 1024 entries, `servers` from 1 to 20, each player
count goes from 0 to 10000 and a plan accepts up to 4096 operations. Text
accepts no Unicode control characters (`Cc`, `Cf` or `Cs`) nor U+FFFD.
Addresses use the explicit grammar `IPv4:port`, `hostname:port` (ASCII labels
without a hyphen at the ends) or `[IPv6]:port`; a form made only of decimal
labels is accepted only when it is a valid canonical IPv4. IPv6 without
brackets and ambiguous endpoints are rejected. QTV streams use
`<decimal-id>@<endpoint>` and ports from 1 to 65535.

`--json` for maintenance stays tied to `--dry-run`; the human output, the
process exit codes and the legacy public `0.7.13` catalog are not changed by
this contract.

## Release

A candidate is prepared only once from the complete commit. Portable
validation, native M3 evidence, approval, publishing the assets, checking the
mirrors and publishing the TUF metadata are distinct gates in the release
workflow; a missing protected configuration fails closed. The local flow stays
useful for rehearsal, but does not replace those gates. The current native
flow runs only on macOS arm64 M3; the names of the other platforms remain
compatibility and preview, not evidence of execution. `candidate.json`
carries `format: 2` and a closed `metadata` map with the size/SHA-256 of
`checksums.txt`, `sbom.spdx.json` and `provenance.json`. It also carries
`candidate_sha256`, computed over its canonical form with that field null;
each payload declares a relative POSIX path and is checked byte for byte
before promotion. The M3 handoff produces a record and a canonical body
outside the candidate; the body binds the manifest by SHA-256 and the
provenance of the run/artifact is checked through the Actions API before the
signed assembly. `release_evidence_binding.py` stays available for private
handoffs that carry raw files, but is not claimed as part of the redacted
input. An explicit `release-evidence.json` is produced only by the protected
assembly workflow after the authorized maintainer's signature under the
ADR 0007 waiver and the validation of the root. That is not independent human
review. Assets precede any optional remote publication and the `current`
pointer; any divergence blocks publication.

For `macOS-ARM64`, the handoff and the native record also carry `hardware`
with exactly `chip` and `model`; `chip` must confirm `Apple M3` (including
Pro, Max or Ultra). Linux, Windows and Intel macOS do not carry that field.
The attestation keeps the generic `macOS`/`arm64` label from being treated as
proof of execution on the M3.

### Legacy signed evidence

When explicitly provided, the aggregate `release-evidence.json` file is
signed over the canonical JSON of the body without the `signatures` field.
The canonical format holds a `signatures` list of `{keyid, sig}` entries; the
legacy singular `signature` form is accepted only for threshold-1
compatibility. Each `keyid` must belong to the `evidence` role of the public
root provided by the ceremony; checking only the format of `keyid/sig` is
never enough. The promotion verifier receives `--trust-root <root.json>` and
validates the 2-of-3 Ed25519 root, the candidate's identity and the signatures
before copying any asset. The private key stays neither in the repository nor
on the runner; the assembly workflow only receives the public envelope the
authorized maintainer produced.

No new runtime, game, map or mod is authorized by this contract.

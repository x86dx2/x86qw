# Contratos públicos da linha 1.0

Este documento define os contratos que precisam permanecer estáveis antes de
uma versão `1.0.0`. A versão pública atual (`0.7.3`) continua imutável; estes
contratos entram primeiro em validação e não mudam o catálogo `current` por si.
O catálogo público `0.7.3` ainda é um documento legado com `format: 1`; a
emissão de `catalog_version` e `min_cli_version` pertence à regeneração e à
assinatura de um catálogo 1.0 posterior.

## Versionamento

- versões de componentes e candidatos seguem SemVer, incluindo `-alpha`,
  `-beta` e `-rc`; componentes numéricos não têm zeros à esquerda e metadados
  de build não alteram precedência;
- o bundle público do instalador permanece, neste contrato, uma versão estável
  `x.y.z`: os validadores históricos e os bootstraps `0.7.x` não aceitam
  prereleases. Uma futura publicação de `alpha`, `beta` ou `rc` exige uma
  alteração explícita do contrato do bundle, dos quatro bootstraps sincronizados
  e da ordenação de `latest`; não é aceita implicitamente pelo gate 1.0;
- cada catálogo, estado e recibo declara sua própria versão de schema;
- documentos com schema explícito também declaram `min_cli_version`; um
  `max_cli_version` só é válido junto com o limite mínimo, e ambos são
  verificados antes de mutação;
- documentos históricos que só carregam `format` continuam legíveis no modo de
  compatibilidade legado;
- clientes antigos usam snapshots imutáveis e não dependem de um `main` móvel.

As versões atuais dos documentos são `catalog_version: 1`, `state_version: 2`
e `receipt_version: 1`. Um documento que escolhe explicitamente uma dessas
versões declara `min_cli_version`; `max_cli_version` é opcional, mas não pode
aparecer sozinho. Documentos legados que só carregam `format` seguem no leitor
de compatibilidade e não são reescritos automaticamente.

### Canais e depreciação

`alpha`, `beta`, `rc` e `stable` são canais SemVer; cada versão publicada
aponta para uma coordenada imutável (`refs/tags/...`, `commit/<sha>` ou
`snapshot/<sha256>`). `nightly` mantém o identificador histórico
`YYYYMMDD-HHMMSS_<sha7>` e também aponta para snapshots imutáveis; um ponteiro
móvel de nightly só pode ser resolvido quando explicitamente habilitado e nunca
é persistido como a identidade consumida pelo cliente. A precedência SemVer é
a oficial: alpha < beta < rc < stable, e metadados de build não alteram a
ordenação.

Depreciações são monotônicas: `active` → `deprecated` → `removed`. Um campo não
pode ser removido sem ter sido previamente marcado como deprecated; qualquer
documento que declare `removed_in` também precisa declarar `deprecated_in` e a
versão removida não pode precedê-la. Clientes devem respeitar a janela de
compatibilidade declarada antes de aceitar uma mutação.

## Estado e saída

`version`, `status`, `hub`, `verify`, `repair --dry-run`, `update --dry-run` e
`upgrade --dry-run` podem produzir JSON canônico sem ANSI, prompts ou segredos.
Os códigos estáveis são `0` (sucesso), `1` (falha operacional), `2` (uso ou
contrato inválido) e `130` (interrupção); nenhum outro código pode aparecer no
envelope JSON público.

Migrações só removem ou substituem um arquivo quando recibo, inventário e
identidade do arquivo provam ownership. Configurações pessoais, demos, logs,
PAKs e arquivos sem ownership comprovado são preservados.

### Envelope JSON e dados por comando

O envelope JSON tem exatamente estes campos: `schema_version` (inteiro `1`),
`command`, `ok`, `exit_code`, `dry_run`, `data` e `errors`. A saída é UTF-8,
canônica, ordenada por chave e termina com uma única quebra de linha; campos
desconhecidos, ausentes ou duplicados são rejeitados. `ok: true` usa
`exit_code: 0` e `errors: []`. `ok: false` usa um código não zero estável,
mantém `data: {}` e traz ao menos um erro com exatamente `code` e `message`.
O campo `dry_run` é sempre `false` para `version`, `status`, `hub` e `verify`,
e sempre `true` para os três comandos de manutenção expostos em JSON.

Para uma resposta bem-sucedida, `data` é fechado por comando:

| comando | forma exata de `data` |
| --- | --- |
| `version` | `{project: "x86qw", version: <SemVer>}` |
| `status` | `{project: "x86qw", target: string, installation: "present"\|"missing", state: "present"\|"missing", sessions: [{session_id: string, status: string, command: string}]}` |
| `hub` | `{target: string, servers: [{address: host:port, title: string, mode: string, map: string, players: {humans: inteiro, bots: inteiro}, qtv_stream: string\|null}]}` |
| `verify` | `{target: string, verified: true}` |
| `repair`, `update`, `upgrade` com `--dry-run` | `{target: string, status: "noop"\|"planned"\|"blocked", operations: [{kind: string, item: string, installed: string, available: string, action: string, size: inteiro\|null}]}` |

As listas de `status.sessions` e `hub.servers` são ordenadas de forma
determinística (`session_id` e `address`, respectivamente), não aceitam
duplicatas nem campos de upstream. O Hub só expõe essa projeção mínima: tokens,
credenciais, URLs com credenciais e o objeto bruto retornado pelo serviço não
fazem parte do contrato. `noop` não contém operações; `planned` contém pelo
menos uma; `blocked` pode ser vazio. A forma de `data` é parte da API: qualquer
mudança de campos, tipos, enumerações ou ordenação exige novo
`schema_version`; clientes devem rejeitar versões que não conhecem.

Para manter a saída previsível, texto em `data` tem no máximo 4096 caracteres;
`sessions` aceita até 1024 entradas, `servers` de 1 a 20, cada contagem de
jogadores vai de 0 a 10000 e um plano aceita até 4096 operações. Texto não
aceita controles Unicode (`Cc`, `Cf` ou `Cs`) nem U+FFFD. Endereços usam a
gramática explícita `IPv4:porta`, `hostname:porta` (labels ASCII sem hífen nas
extremidades) ou `[IPv6]:porta`; uma forma composta somente por labels
decimais só é aceita quando for um IPv4 canônico válido. IPv6 sem colchetes e
endpoints ambíguos são rejeitados. Streams QTV usam
`<id-decimal>@<endpoint>` e portas de 1 a 65535.

`--json` para manutenção continua condicionado a `--dry-run`; a saída humana,
os códigos de processo e o catálogo público legado `0.7.3` não são alterados
por este contrato.

## Release

Um candidato é preparado uma única vez a partir do commit completo e verificado
diretamente no Mac antes da promoção local. Não há jobs, artifacts, metadata
externa ou runner necessários para essa sequência. O fluxo atual roda somente
no macOS; os nomes de plataformas nativas permanecem compatibilidade, não uma
exigência de execução. O `candidate.json` carrega
`format: 2` e um mapa fechado `metadata` com tamanho/SHA-256 de
`checksums.txt`, `sbom.spdx.json` e `provenance.json`. Ele também carrega
`candidate_sha256`, calculado sobre sua forma canônica com esse campo nulo; cada
cada payload declara um caminho POSIX relativo e é conferido byte a byte antes
da promoção. Um `release-evidence.json` explícito continua sendo
compatibilidade opcional e é validado sem ser gerado pelo fluxo Mac. Assets
precedem qualquer publicação remota opcional e ponteiro `current`; qualquer
divergência bloqueia a publicação.

### Evidência assinada legada

Quando fornecido explicitamente, o arquivo agregado `release-evidence.json` é assinado sobre o JSON canônico do
corpo sem o campo `signatures`. O formato canônico contém uma lista
`signatures` de entradas `{keyid, sig}`; a forma legada singular `signature` é
aceita somente para compatibilidade de threshold 1. Cada `keyid` precisa
pertencer ao papel `evidence` do root público fornecido pela cerimônia;
conferir apenas o formato de `keyid/sig` nunca é suficiente. O verificador de promoção recebe
`--trust-root <root.json>` e valida RSA-PSS-SHA256, identidade do candidato e
cadeia de rotação antes de copiar qualquer asset. A chave privada não fica no
repositório nem no runner. Esse caminho não participa da preparação ou promoção
Mac atual; relatórios de plataforma individuais não são coletados pelo
checkout atual.

Nenhum runtime, jogo, mapa ou mod novo é autorizado por este contrato.

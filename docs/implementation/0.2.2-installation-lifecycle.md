# Implementation note — corrective lifecycle for 0.2.2

This note records the corrective code that followed the public release `0.2.1`.
It neither prepares nor authorizes the publication of `0.2.2`.

## Baselines

- published release: tag `x86qw-installer-0.2.1`, commit `527d0d1006`;
- code first analyzed: `main` at
  `2c832762f6ac2fbebf7cfc7f925c13b9353f102a`;
- public version throughout the fix: `0.2.1`;
- documentation HEAD: the corrective branch that holds this note, until the merge;
- initial tests: 253 maintenance tests and four site tests, with two
  documented platform skips.

## Reproduced defects

- only `host`, `proxy` and `qtv` had a lock; maintenance could change or
  remove an installation while the stack used its files;
- recovery trusted the children, but did not check the controller's identity
  recorded in the journal when `active.lock` was missing;
- sensitive temporaries still recorded a hash and used a removal able to
  walk a directory put in place of the file;
- a failure during cleanup could prevent the attempt to release the lock;
- the POSIX leader could exit while a descendant of the group survived;
- Windows processes did not belong to a Job Object;
- the client assessment queried the catalog before recognizing purely local
  repairs.

## Fixed contract

`session_control.py` is the only implementation of the lock. Format 2 tells
`service` from `maintenance`, and the reader still accepts `0.2.1`'s format 1.
Every mutating action and its dry-run acquire the same lock before
reading an operational snapshot or changing the destination. `version`, `verify`, `hub` and
`play` stay available; `play` still does not mutate the payload.

The old CLI's handoff in `update` and `upgrade` only downloads and validates. The
final process, started with `--skip-cli-update`, acquires the lock and performs the whole
mutation. If a stack starts in the meantime, the final process aborts before
changing the installation.

## Recovery and secrets

Every journal is validated before any action. A live or
inconclusive controller blocks recovery even without a lock. A legacy journal without
identity is only recoverable when every child is provably
dead or diverging.

`sensitive: true` entries hold no `expected_hash`, content or arguments.
The sensitive cleanup removes only a regular file or a symlink. A directory or
special file is preserved, produces a diagnosis and makes the finalization
unsuccessful. Modified non-sensitive material is still preserved.

## Processes and finalization

The journal, ephemeral content, stage and lock steps are attempted
independently. Cleanup errors are reported without hiding the original error;
a critical failure after a successful operation produces a nonzero code.

On Unix, the group is checked after `SIGTERM`, even when the leader has already
ended, and gets `SIGKILL` if it still exists. On Windows, the APIs used have
explicit `ctypes` signatures and each process is assigned to a Job Object with
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.

## Offline repair

The assessment checks the receipt, runtime, format, hash, permission and macOS
preparation before querying the catalog. AppImage and service permissions, plus
local macOS preparation, can be fixed offline. A missing or diverging payload
still gets no download through the installed CLI and points to re-running the
bootstrap on the same destination, keeping the recorded channel and version.

## Deliberate limits

The portable tests and the CI matrix are not the same as a native smoke of the runtimes.
Graphical smokes, real MVD, real forwarding and full native execution per
platform stay pending in the roadmap. No runtime, game, mod, map,
gameplay, PAK or profile was added or changed in this fix.
